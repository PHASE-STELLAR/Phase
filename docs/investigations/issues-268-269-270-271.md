# Investigation: issues #268, #269, #270, #271

## Summary

All four issues share an identical templated body — the same "Horizon
ingestion lag / Classic LIQ / `mint_and_settle` double-mint" description,
"why this is hard" section, and a six-step CRDT/`yjs`/signal-store task list,
copy-pasted verbatim across all four with only a number substituted (077,
078, 079, 080). None of that boilerplate has anything to do with the actual
titles.

Each issue does carry one "evidence" bullet naming a real file with a line
range — those were checked directly against the current codebase. In every
case the cited range does not contain the code the bullet describes:

| Issue | Evidence cited | What's actually at that location |
| --- | --- | --- |
| #271 | `lib/market-store.ts:42-118` — "`amount` `string` `vs` `number`" | Zod schema, JSON read/write helpers, view-analytics hashing. No amount/sort logic in this range. |
| #270 | `lib/phase-nft-metadata-build.ts:44-78` — "`isGated` `Map` `5min`" | IPFS gateway fallback config resolution and gateway-health reordering. No `isGated` identifier exists anywhere in this repository. |
| #269 | `lib/distributor-health-store.ts:18-34` — "`poll` `1s`" | Type definitions and a file-path helper. No polling loop of any kind in this file. |
| #268 | `app/api/world/[collection_id]/export/route.ts:11-34` — "`without` `viewerSignature`" | This range is real (the `GET` handler), but see below. |

## Per-issue findings

**#271 — market-store amount sort.** `price_phaselq` and `amount_phaselq`
are typed as `number` (`lib/market-store.ts:18,35`) and stored as SQLite
`REAL` columns (schema: `price_phaselq REAL NOT NULL`). The only sort sites
(`ORDER BY price_phaselq ASC/DESC` in `getListings`, and
`(a, b) => b.price_phaselq - a.price_phaselq` in the order-book builder) are
both numeric comparisons. No lexicographic string-sort bug exists.

**#270 — phase-nft-metadata-build gated-metadata leak.** Searched the entire
repository for `isGated` — zero matches. `lib/phase-nft-metadata-build.ts`
has no gating or visibility concept at all; it's IPFS gateway fallback and
metadata-fetch retry logic. There is no cache or memoization keyed on a
gating flag anywhere in this file for a public/gated leak to occur through.

**#269 — distributor-health-store poll rate.** The health check in
`lib/distributor-health-store.ts` runs on an `intervalMinutes`-based cadence
driven by `/api/cron/faucet-health` (a cron-triggered route), not a
client-side 1-second loop. Searched the whole app for `setInterval` calls:
the only 1000ms interval is an unrelated UI clock tick in
`components/faucet-modal.tsx` (`setInterval(() => setNow(Date.now()), 1000)`)
that has nothing to do with Horizon polling or this store.

**#268 — world export without a viewer check.** This one's evidence location
is real: `app/api/world/[collection_id]/export/route.ts`'s `GET` handler
takes no wallet/signature parameter and calls `buildWorldExportSnapshot`
unconditionally. However, checking the rest of the world-reading surface
(`app/api/world/[collection_id]/route.ts`, `app/api/narrator/route.ts`)
shows every other world/narrative read endpoint in this app is equally
unauthenticated by design. The only access control that exists anywhere in
`lib/narrative-world-store.ts` is on *role assignment*
(`setWorldRole` requires the caller to be the stored `owner`, and
`app/api/world/[collection_id]/roles/route.ts`'s `POST` requires an
`X-Wallet-Signature` header) — there is no `is_private`/`visibility` field on
a world anywhere in the data model, and no other route treats world content
as private. The export route returns the same fields (`world_name`,
`world_prompt`, `narratives[].narrative`, `.lore_input`) that the plain
`GET /api/world/[collection_id]` and narrator routes already expose with no
auth. So while the route is technically unauthenticated, it is not exposing
anything beyond what this app already treats as public read data — the
"private World leak" framing doesn't match the app's actual data model.

## Recommendation

No code change is proposed in this PR. If world content is *intended* to
support a private/owner-only mode, that's a real product decision (a
visibility field on `WorldCollectionData`, enforced consistently across
every read route, not just export) — worth its own issue with an accurate
description, distinct from #268 as currently written. #269, #270, and #271
don't correspond to any defect in the current code and are recommended to be
closed as invalid, pending the reporter providing evidence that actually
matches the codebase.
