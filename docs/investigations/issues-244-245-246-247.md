## #244 — "retry storm: fixed 100ms `txBadSeq` retry → 300 retries → 429"

**Not reproducible. No code change.**

- No `replayDeadLetter` symbol exists anywhere in the repository
  (`grep -rn "replayDeadLetter"` returns nothing).
- `lib/x402-dead-letter.ts` contains no retry logic and no timer at all. It is
  the phase-144 malformed-invoice *quarantine* module: `X402InvoiceSchema`,
  `classifyInvoice()`, `redactSecrets()`, and a JSON dead-letter store with an
  operator review surface (`listDeadLetterQueue`, `resolveDeadLetterEntry`).
  Nothing in it submits a transaction, so it cannot produce a retry storm.
- No `txBadSeq` handling exists anywhere in the repository either.
- The fixed-interval-retry problem the issue describes is in fact already
  handled, in the module that does talk to Horizon: `lib/classic-liq.ts:397-415`
  `submitTrustlineWithRetry()` retries only on 429/503, with exponential
  backoff plus jitter (`baseDelayMs * 2 ** (attempt - 1) + jitterMs`) and a
  bounded attempt count (default `maxRetries = 3`, `baseDelayMs = 500`), behind
  the `phase-134` flag, alongside a bounded-concurrency batch submitter. That is
  the anti-retry-storm design the issue asks for, already in place.

Nothing to change. Recommend closing as not reproducible.

## #245 — "sybil graph false positive: `sameDistributor` 1h window flags legit world creator"

**Not reproducible. No code change.**

- No `sameDistributor` function exists anywhere in the repository
  (`grep -rn "sameDistributor"` returns nothing), nor does any 1-hour time
  window, cluster size threshold, or follower-count heuristic.
- `lib/sybil-resistance.ts` is a pure feature-vector scorer, not a graph. It
  exports `scoreWalletHistory()`, which sums weighted signals — account age,
  transaction count, distinct counterparties, native balance, home domain,
  signer count, trustline count, sponsored reserves — into a 0..100 score, then
  bands it `trusted` / `caution` / `suspect` against `SUSPECT_MAX` (34) and
  `CAUTION_MAX` (64). `SybilScoreInputSchema` has no follower or distributor
  field, so a "+10 followers" signal cannot influence the score at all.
- The general worry — a legitimate, established account being scored
  `suspect` — is a threshold-tuning question, not a defect. Changing the
  weights or the `SUSPECT_MAX` cutoff without a concrete repro would be
  guesswork, and would weaken the faucet protection this module exists to
  provide. If a real false positive is observed, it needs the wallet address
  and the returned `signals` array.

Nothing to change. Recommend closing as not reproducible, or reopening with a
concrete scoring repro.

## #246 — "faucet: turnstile + `visitorId` spoof → 10k sybil → 100k XLM drain"

**Reported vector not reproducible. No code change.**

- No `visitorId`, `fingerprintjs`, or any client fingerprint field exists
  anywhere in the repository. The `POST` body type is
  `{ walletAddress, userAddress, reward, referralCode, turnstileToken, hashcashProof }`
  (`app/api/faucet/route.ts:496-498`).
- The Turnstile check is **not** client-trusted, which is the substance of the
  claim. `verifyTurnstileToken()` (`lib/faucet-turnstile.ts:57-93`) posts the
  token together with the server-held `CLOUDFLARE_TURNSTILE_SECRET` to
  Cloudflare's `siteverify` endpoint and requires `success: true`; a non-OK HTTP
  status, a `success: false` body, or an 8s timeout all reject. The route
  requires a token when a site key is configured and returns 400/403/500
  otherwise (`route.ts:524-551`). A spoofed client-side result cannot pass this,
  because the client result is never consulted — only Cloudflare's response is.
- The claim already carries two independent server-side gates ahead of any
  payout: the governance deny-list (`route.ts:512-521`) and on-chain sybil
  scoring (`route.ts:554-568`).

**Separate observation, deliberately not changed here.** The hashcash layer is
inert scaffolding rather than a live drain vector: `hashcashProof` is accepted
in the request body but never validated in the handler, no challenge is ever
issued to a client, and `verifyHashcashProof()` (`lib/faucet-turnstile.ts:111-133`)
does not actually hash — it accepts any `counter >= 2 ** difficulty`, with an
in-file comment noting a real implementation would use `crypto.subtle.digest`.
So there is no proof-of-work protection in effect, but equally no code path
that trusts one. Wiring it up is a feature decision (challenge issuance,
difficulty tuning, storage of outstanding challenges) that this issue does not
describe, so it is flagged here rather than implemented.

Nothing to change for the reported vector. Recommend closing as not
reproducible, and filing a separate issue if the hashcash layer is meant to be
live.

## #247 — "RBAC: `POST` role assignment without admin auth → privilege escalation"

**Real, and fixed in this PR.** This is the one issue of the four whose cited
file contains the described weakness.

The endpoint guards role assignment with a presence-only header check:

```ts
if (!request.headers.get("x-wallet-signature")?.trim()) { /* 401 */ }
```

That proves nothing. `acting_wallet` is read from the **request body**, and
`setWorldRole()` (`lib/narrative-world-store.ts:264-280`) grants the role when
`entry.owner === actingWallet`. Since the signature was never verified, any
caller could set `acting_wallet` to the world owner's address, send any
non-empty `x-wallet-signature` value, and assign a role to any wallet. The
client side confirms the header was never a real signature — `app/signals/page.tsx:410`
sends the literal address as the "signature". So the check added by #291 / PR #340
is cosmetic, and the escalation the issue describes is reachable by anyone.

The title's `role: 'admin'` detail does not apply: the route only accepts
`editor` or `viewer` and 400s on anything else, so the escalation is to
`editor`/`viewer` on a world you do not own rather than to an `admin` tier.
`WorldRole` has no `admin` variant.

### Fix

- `lib/viewer-signature.ts` — added `canonicalWorldRolePayload()`,
  `worldRoleProofMessage()`, and `verifyWorldRoleSignature()`, mirroring the
  module's existing SEP-53 helpers for community signals. The proof binds to the
  action, not just to the signer: `action`, `collection_id`, `target_wallet`,
  `role`, `timestamp`. Verification is `Keypair.verify` over
  `SIGNATURE_PREFIX + message`, so a signature captured for one assignment
  cannot be replayed for a different role, collection, or target.
- `app/api/world/[collection_id]/roles/route.ts` — the header is now required to
  verify against `acting_wallet` before `setWorldRole()` is reached, and the
  client-supplied `timestamp` must be present and within a 5-minute window so a
  captured request cannot be replayed later.

`setWorldRole()`'s own ownership check is left in place as the second line of
defence. No client calls this endpoint today (the route is currently
server-only), so the added requirement breaks no existing caller.
